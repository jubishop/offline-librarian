## Findings

### F1: An unfinished from-scratch rebuild drops vectors  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** librarian/meaning.py:259
- **scope:** in-diff
- **concern:** a new `library.sqlite` has no `builds` row until its first build finishes, so `_builds` returned None, which differed from the store's checked count, and a pass during the build dropped the vectors of every source not built yet (Wikipedia's are about three days of embedding), contrary to the guard the PR and design describe
- **resolution:** a finished build now records a new random id as `build`; the run skips while a library with a `meta` table has none, and the id can't repeat across library files; `test_keeps_vectors_until_a_library_rebuilt_from_scratch_is_done` covers it
- **fixed_at:** 2026-11-02

### F3: A rebuild from scratch during a pass passes the guard  (fixed)

- **severity:** Warning
- **status:** fixed
- **location:** librarian/meaning.py:388
- **scope:** in-diff
- **concern:** `drop_unused` read the build id from the connection the pass opened, which keeps reading a deleted `library.sqlite`, but found unused vectors in a fresh connection to the new file, so a rebuild from scratch started during a pass that embeds an unchecked build dropped the vectors of every source the new library lacked
- **resolution:** both now come from one fresh connection, reading `main.meta` since the attached store has a `meta` table too; `test_keeps_vectors_when_the_library_is_rebuilt_from_scratch_during_a_pass` covers it
- **fixed_at:** 2026-11-02

### F4: A build's finish can go unrecorded  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** librarian/build.py:195
- **scope:** in-diff
- **concern:** a build interrupted during its long index optimize records no id and its rerun changes nothing, and a no-op build on a pre-change library creates an empty `meta` table, so the vectors left unused stay until a later build changes the library
- **resolution:** it errs toward keeping vectors and recovers at the next build that changes something; the cost is disk and slightly slower searches for up to a month, which doesn't justify extra state or a fault-injection test

### F5: A library in its first instant reads as built before builds were recorded  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** librarian/meaning.py:258
- **scope:** in-diff
- **concern:** `_last_build` returns None for any library without a `meta` table, including the empty file a from-scratch build creates just before its schema, so a pass whose `drop_unused` reads it then, with a checked id stored, finds every vector unused once the schema appears and drops them all
- **resolution:** it needs that rare manual rebuild and the worker's check, once per 10-minute poll, to land in the sub-millisecond gap before `meta` exists; the worker re-embeds what was lost. If rebuilds from scratch become routine, read `sqlite_master` once and treat only passages without `meta` as pre-change

### F6: Dropping holds the exclusive lock for every row at once  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** librarian/meaning.py:167
- **scope:** in-diff
- **concern:** `drop` deletes all unused rows in one transaction under `moving()`, so a search can wait seconds rather than the one batch the design describes: about 2 s for the real store's one-time drop, and over 10 s for an edition that re-keys a million passages
- **resolution:** it happens once per changing build, a search in that window only waits and never reads a moved row, and batching it isn't worth another change
